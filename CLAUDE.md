# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Streamlit app (`app.py`) that queries a production MySQL database (`checkpoint_live`, on AWS RDS) and builds a client-wise case/check report. It has grown from a single download button into a small report-building tool:

- Filterable fetch (date range, client, check name, case/check status, check severity).
- A drag-and-drop column picker with pivot-table-style aggregation (hide a column that distinguishes rows → those rows collapse into one).
- Optional per-check "antecedent field" enrichment (`ec_case_check_data`), added as extra columns without bloating the main query.
- Several "split into one file per X" downloads (client, Process Name, Location, a Case Flex Field, an antecedent field), each with an optional Outlook-based bulk-email flow.
- A **Saved Trackers** view: named, reusable filter presets stored in a local SQLite file, with Edit / Email / Download / Active-Inactive actions.

There is no build step and no test suite — everything is plain Python files run directly by Streamlit.

## Commands

```bash
pip install -r requirements.txt
streamlit run app.py              # default port 8501; pass --server.port N if it's taken
```

No linter, formatter, or test suite is configured in this repo. `pywin32` (Windows-only, guarded by `sys_platform == "win32"` in requirements.txt) is needed for the Outlook email feature — see below.

## Architecture

Streamlit re-runs `app.py` top-to-bottom on every widget interaction — there is no separate component tree or client/server split to reason about, just this one script's control flow. `app.py` renders one of two "views" via a `st.segmented_control` (`BUILDER_VIEW` / `TRACKERS_VIEW`) rather than `st.tabs`, specifically so code can switch the active view programmatically (see the Saved Trackers section below) — `st.tabs` has no such API.

- **`db.py`** — SQLAlchemy engine (`mysql+pymysql`) built from `.env` (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`). `run_query_params(query, params)` is the one way queries get executed against MySQL: list/tuple/set param values are automatically bound as expanding `IN (:list)` parameters via SQLAlchemy's `bindparam(..., expanding=True)`. This is the *only* place in the app that writes to or reads from MySQL — nothing else does, including the new Saved Trackers feature (see `tracker_store.py`).
- **`queries.py`** — every raw SQL string used by the app, as module-level constants.
  - `CASE_REPORT_QUERY` is the main report query. It takes five string-formatted placeholders — `{client_filter_clause}`, `{check_name_filter_clause}`, `{case_status_filter_clause}`, `{check_status_filter_clause}`, `{check_severity_filter_clause}` — each filled with its matching `..._FILTER_CLAUSE` constant or `""` depending on whether that filter is active. Empty selection means "no filter", not "match nothing". `CASE_STATUS_FILTER_CLAUSE`/`CHECK_STATUS_FILTER_CLAUSE` filter on `checkpoint_live.fn_case_status(...)`/`fn_check_status(...)` — the *translated* expression the SELECT list itself uses — so a picked filter value lines up with what the report displays, not a raw DB code.
  - The query docstring documents several hand-fixed bugs (an alias collision between `ec_client` and `ec_checks`, a duplicate-column name across interim/final report severity, a contact-details fan-out fixed via correlated subquery) — don't reintroduce those.
  - **Lookup query performance is easy to get catastrophically wrong here — see "Lookup query performance traps" below before touching any of `CASE_STATUS_LOOKUP_QUERY`, `CHECK_STATUS_LOOKUP_QUERY`, `CHECK_SEVERITY_LOOKUP_QUERY`/`..._BY_CLIENT_QUERY`, or `FIELD_NAME_LOOKUP_QUERY`.**
  - `ANTECEDENT_DATA_QUERY` pulls `ec_case_check_data` rows (stated/verified per-check custom field values) scoped to specific `field_names` + `case_check_ids` — see "Antecedent fields" below for why this is never joined into `CASE_REPORT_QUERY` directly.
- **`app.py`** — everything UI lives here, rendered in this order inside `BUILDER_VIEW`: Filters → Save/Update Tracker → Fetch Report button → Add Antecedent Fields → Customize Columns → Report Preview → the two original downloads → More Ways to Split (with per-split email panels). `TRACKERS_VIEW` is a separate function, `render_saved_trackers_view()`.
  - `get_client_lookup()`, `get_check_name_lookup()`, `get_case_status_lookup()`, `get_check_status_lookup()`, `get_check_severity_lookup()`, `get_field_name_lookup()` are the `@st.cache_data(ttl=3600)`-memoized lookups that populate the filter/picker widgets. Several of them have two code paths for a *performance* reason, not a stylistic one — see "Lookup query performance traps" below.
  - The Company Name, Unique Check Name, Case Status, Check Status, and Check Severity filters are all independent (AND semantics when several are set, not mutually required).
  - `run_tracker_query(cfg)` builds and runs `CASE_REPORT_QUERY` (plus any saved antecedent fields) from a plain config dict rather than live widget values — shared by the interactive Fetch button, Saved Trackers' "Download", and "Email Tracker" actions, so all three behave identically.
- **`report_excel.py`** — builds every downloadable `.xlsx`/`.zip` from a fetched `DataFrame`.
  - `aggregate_selected_columns(df)` — the pivot-table-style collapse: `df.drop_duplicates()` on whatever columns are currently visible. No dedicated "Record Count" column (removed per feedback — just fewer, deduplicated rows).
  - `build_report_excel(df, columns=None)` / `build_split_report_zip(df, flex_map, columns=None)` — the original two downloads (single sheet; one `.xlsx` per client with that client's own flex-field names via `flex_fields.py`).
  - `build_group_split_zip(df, group_column, columns=None)` — the generic "split by any column" used for Process Name / Location / a Case Flex Field / an antecedent field. Written incrementally (one group's workbook built and flushed into the open zip at a time, via `df.groupby(...)`'s lazy iteration) so peak memory is one group's data, not the whole report. Raises `TooManySplitGroupsError` up front if the column has more than `MAX_SPLIT_GROUPS` (300) distinct values — refuse rather than silently build hundreds of one-row files.
  - `build_single_group_excel(df, group_column, group_value, columns=None)` — one group's workbook on its own, used when emailing a single split file instead of generating/unzipping the whole batch.
  - `build_mapping_template_excel(dimension_label, values)` — the downloadable starter file for a split's email mapping upload (one row per distinct value, blank `To_address`/`CC_address` columns).
  - `sanitize_filename(name, used, max_len, fallback=...)` — public (not `_`-prefixed) since it's reused outside this module for antecedent-field email attachment names.
- **`flex_fields.py`** — `load_flex_field_map()` reads `ec_client_case_fields` and returns `{client_external_id: {field_index: field_name}}`, resolving multiple rows per field index by keeping the highest `client_field_id` (most recent). `flex_column_rename_map()` turns that into a per-client `{"CASE_FLEX_FIELDn": "Real Name"}` rename dict, falling back to `"Flex Field n"` for indices the client has no mapping for. Only used by the split-by-client path.
- **`outlook_email.py`** — Outlook desktop COM automation via `pywin32`, used for all "email a split file" flows. No SMTP — `send_via_outlook(...)` is the only function that talks to Outlook, so swapping to SMTP later means replacing this module's internals, not its callers. `outlook_available()` does a lazy `import win32com.client` so the module still imports cleanly on non-Windows machines or without `pywin32` installed; the UI checks it and disables emailing instead of crashing. Attachments are written to a private temp directory first (Outlook's COM API needs a real file path, not in-memory bytes) and cleaned up after send, success or failure.
- **`tracker_store.py`** — local SQLite persistence (`trackers.db`, created next to the app) for Saved Trackers. **Deliberately not the MySQL DB** — that database is read-only everywhere else in this app, and adding a table/write path there would be a much bigger, harder-to-reverse change than this feature needed; ask before changing that decision. `save_tracker(config, tracker_id=None)` inserts when `tracker_id` is `None`, updates otherwise, and always returns the row's id — callers must capture that return value back into session state or a second save duplicates instead of updating. A tracker's date range is stored as `lookback_days` (rolling window resolved against *today* at run time), not frozen From/To dates, so a tracker saved once and reused months later still pulls fresh, relevant data instead of replaying a range that's aged out. `current_user()` (OS login username via `getpass.getuser()`) stands in for "Modified By" — this app has no login system of its own.

### Key schema concept: two different "check name" columns

`ec_case_checks.check_name` (aliased `ecc.check_name`, exposed as `check_name`) is per-case-instance and gets mangled in practice (numbered suffixes like `(1)`/`(2)`, occasional duplicated text). `ec_checks.check_name` (aliased `ec.check_name`, exposed as `Check_unique_name`) is the clean, canonical name from the master check catalog for that `check_id`. The "Unique Check Name" filter and its lookup queries are keyed on `ec.check_name`, not `ecc.check_name` — that distinction is intentional, not a naming accident.

### Lookup query performance traps (all previously caused real multi-second-to-timeout hangs)

Every one of these was hit and fixed during development — the fix is encoded in the current query/code, but it's easy to "simplify" back into the slow version by accident:

- **Translate-then-dedupe vs dedupe-then-translate.** `CASE_STATUS_LOOKUP_QUERY`/`CHECK_STATUS_LOOKUP_QUERY` need the small set of *translated* status labels (`fn_case_status`/`fn_check_status` applied). Naively written as `SELECT DISTINCT fn_case_status(case_status) FROM ec_case_master`, MySQL evaluates the function on every row before deduping — 30s+. The fix: dedupe the raw numeric codes first in a subquery, then translate only that handful of values (`SELECT fn_case_status(codes.case_status) FROM (SELECT DISTINCT case_status FROM ec_case_master WHERE ...) codes`) — ~2-3s.
- **Client-scoped joins don't scale with client count.** An early version of the antecedent field-name lookup joined `ec_check_fields`/`ec_case_check_data` through `ec_case_checks`/`ec_case_master`/`ec_master_company`/`ec_client` to scope by selected client(s). Fine for one client (~2.7s), but timed out at 60s+ once a report spanned more than ~30 clients — the join just doesn't scale with client count. `FIELD_NAME_LOOKUP_QUERY` instead scopes directly by the report's own `Case_Check_id` values (the same set already used to pull the antecedent data itself), skipping that join chain entirely: ~3-6s even for 5,000-20,000 ids, regardless of how many clients they span. If you're tempted to add a "scope by client" lookup for a new dimension, scope by the already-fetched row-level ids instead.
- **`check_severity` has no cheap lookup, full stop.** Unlike case/check status, it's a free-text legacy column with ~140 messy distinct values across the whole table, and a plain `SELECT DISTINCT check_severity` — with or without date scoping — was measured at 50s+ (the underlying table scan is the bottleneck, not the row count, so scoping by date doesn't help either). `CHECK_SEVERITY_LOOKUP_BY_CLIENT_QUERY` (scoped to selected client(s), ~2-3s) is used automatically when a client is selected; the unscoped `CHECK_SEVERITY_LOOKUP_QUERY` is only ever run on an explicit "Load all severity options (~1 min, slow)" button click, never eagerly.
- **Antecedent fields are opt-in for the same reason.** The whole "Add Antecedent Fields" section is gated behind an unchecked-by-default checkbox — even at ~3-6s, that cost should never be paid by a user who doesn't want the feature on that particular fetch.

### Streamlit gotchas worth knowing before touching the UI code

- **`st.expander(..., expanded=...)` re-evaluates on every rerun.** If `expanded` is computed from state that doesn't itself flip on every interaction inside the expander (e.g. `expanded=bool(some_flag)`), the panel visibly snaps shut the moment the user interacts with anything inside it that triggers a rerun (a file upload, a button) — because Streamlit doesn't remember "the user had this open," it just re-evaluates the expression. Every expander in this app that has live interaction inside it (the antecedent/flex/process/location email panels, the Save Tracker panel) uses `expanded=True` unconditionally for this reason.
- **You cannot set `st.session_state[key]` for a widget that already rendered earlier in the same script run.** Streamlit raises `StreamlitAPIException`. This bit the Saved Trackers "Edit"/"Email" buttons: they're rendered inside `render_saved_trackers_view()`, which runs *after* the `st.segmented_control(..., key="view_switch")` call has already executed on that same pass — so they can't do `st.session_state.view_switch = BUILDER_VIEW` directly. The fix is the `pending_view` indirection: the button handler sets `st.session_state.pending_view` and calls `st.rerun()`; the very first lines of the script (before any widget renders) check for `pending_view` and apply it to `view_switch` *then*. The same pattern (`pending_tracker_load`) is used to pre-fill the Filters widgets (`flt_client_labels`, `flt_check_names`, `flt_from_date`, etc.) before they're instantiated.
- **A bare button + text_input can race and silently drop the just-typed value.** A `st.text_input` only pushes its value to `session_state` on blur, sent as its own message — not guaranteed to be fully applied before a fast-following button click's message is processed. The Save Tracker Name/Description fields hit this in testing (description saved as blank despite being visibly typed). Fixed by wrapping the inputs and both save buttons in one `st.form(...)`: a form's submit bundles every contained widget's current value into a single atomic message, so there's no ordering race. Any future "type something, then click a button that reads it" UI should use a form for the same reason.
- **Widgets shouldn't combine `value=` with a `key=` you also set programmatically.** Passing both makes Streamlit print a "widget had both a default value and a Session State value" warning whenever the programmatic set actually fires (e.g. loading a tracker's saved dates into `flt_from_date`/`flt_to_date`). Seed the default into `session_state[key]` once (`if key not in st.session_state: ...`) instead of passing `value=` on the widget call.
